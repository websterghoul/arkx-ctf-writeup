2.1 Bad Robot — Code Injection via eval()

Challenge: Advanced track, level 5 — Bad Robot  ·  Vulnerability class: Code injection via eval() in a tool  ·  Severity: Critical  ·  Verified flag: flag-1a094e

Mechanism

The level presents itself as a “Math Calculation Service. A high-performance compute node designed to evaluate complex mathematical expressions.” It exposes exactly one tool:

GET /level/5/tools  ->  {"tools":[{"name":"calculate",
    "description":"A powerful calculator that can evaluate complex mathematical expressions."}]}

The tool does not parse arithmetic. It hands the user string to a Python eval(), so any valid Python expression — including function calls, attribute access and file I/O — is a legitimate “expression”:

# vulnerable pattern
def calculate(expression: str):
    return eval(expression)     # input executed as code, not evaluated as data

# safer pattern: parse an AST, allow only arithmetic node types
import ast, operator
ALLOWED = {ast.Add: operator.add, ast.Sub: operator.sub,
           ast.Mult: operator.mul, ast.Div: operator.truediv}
def safe_eval(expr):
    node = ast.parse(expr, mode='eval').body  # walk node; permit only Constant/BinOp

Two half-measures are layered on top and both fail: a substring blocklist that rejects a handful of dangerous words, and an output formatter that only renders numeric results. Neither bounds the capability; they only decorate the response.

Verified result

Exploited live and accepted by the platform. flag-1a094e  ·  the platform’s own status endpoint confirms the level is completed:

Root cause

The design error is treating user input as code rather than as data validated against a schema. A Turing-complete evaluator is given to a component whose job is a narrow, well-defined operation (arithmetic), so the tool’s capability is far broader than its purpose — excessive agency at the tool layer.

Two failure modes compound it:

  • The control is a blocklist, and blocklists lose. Refusing the literal strings os and popen changes nothing when the language can rebuild those names at runtime ("o"+"s") and has a dozen other routes to the same capability. The filter inspects the payload, not the operation.
  • The exception path is a disclosure channel. The response formatter was designed to hide non-numeric values — but the handler that catches evaluation errors echoes the interpreter’s message verbatim, and that message contains the value that was rejected. The “hide the output” rule is defeated by asking the interpreter to complain about the output.

Impact & severity

Severity: Critical.

Arbitrary Python execution in the context of the process that hosts the calculator. In this level that is enough to read flag.txt; the same primitive reads any file the process can open, reaches the network from the container, and in a real deployment would harvest environment credentials and enable persistence. The blast radius is the host, not the conversation.

Mapping

OWASP Top 10 for LLM Applications 2025

  • LLM05:2025 — Improper Output Handling — attacker-controlled text reaches a downstream interpreter.
  • LLM06:2025 — Excessive Agency — the tool can do far more than its stated function.

MITRE ATLAS

  • AML.T0053 LLM Plugin Compromise — a trusted tool interface is used to execute unauthorized actions.

Prevention

  • No dynamic execution: never pass user input to eval(), exec() or equivalent. Use a dedicated expression parser.
  • Allowlist, not blocklist: parse to an AST and permit only an explicit set of node types and operators.
  • Validate inputs: enforce strict schemas on every tool input before it reaches any interpreter.
  • Sandbox by default: run anything that must execute code with minimal file-system, network and credential privileges.
  • Never echo interpreter errors to the client: return a generic failure and log the detail server-side — here the error text was the exfiltration channel.

Platform note shown after the solve (“lessons learned”)

The level UI shows this note in a popup the moment the flag is accepted. It is reproduced verbatim — it is the challenge designer’s statement of the same root cause.

Code Injection via eval()

What happened: The calculator tool used eval() to execute user input as Python code, allowing arbitrary code execution including file system access.

Why it's dangerous: Code injection vulnerabilities allow attackers to execute arbitrary commands, access sensitive data, modify system behavior, or establish persistent access.

Prevention:

  • Never use eval(), exec(), or similar functions with user input
  • Use safe expression evaluators or mathematical parsers instead
  • Validate and sanitize all inputs according to strict schemas
  • Run code in sandboxed environments with restricted permissions
  • Use allowlists of permitted operations rather than trying to block dangerous ones

Key lesson: eval() is dangerous. If you need dynamic code execution, use safer alternatives or run in heavily restricted sandboxes.

2.2 Master of Resources — Sensitive Data Exposed Through an MCP Server

Challenge: Advanced track, level 7 — Master of Resources  ·  Vulnerability class: Sensitive resource exposed via an MCP server  ·  Severity: High  ·  Verified flag: flag-d39d05

Mechanism

The chat agent is a decoy: it is scripted to answer the same sentence forever, while the level’s real interface is an MCP (Model Context Protocol) server left running. The interface banner says it outright — “The main interface is down, but the underlying resource server remains accessible for API calls.”

That server registers protected content in its public catalogue and “protects” it with another tool that the same client may call:

tools:      unlock_flag    — "Unlocks the flag resource, allowing it to be accessed."
resources:  resource://flag          (mimeType text/plain)
            resource://super-secret  (decoy)

MCP is an exposes-to-the-client protocol: resources/list is delivered in full to every connected session. Anything registered there is therefore public, and the “lock” is a state variable flipped by a tool the caller can invoke. A control that the untrusted party can operate is not a control.

Verified result

Exploited live and accepted by the platform. flag-d39d05  ·  the platform’s own status endpoint confirms the level is completed:

GET /level/7/status  ->  {"level":7,"accessible":true,"completed":true,"session_id":"cb7fea139975"}

Root cause

Authorization is implemented at the wrong layer. The application relies on the MCP transport (and the web session cookie protecting the surrounding page) to gate access, while the MCP server treats every connected session as fully trusted. MCP servers are built for discoverability and transparency; they are not an access-control boundary. Putting protected data inside that boundary, instead of behind a backend with real per-caller authorization, is the structural mistake.

Three smaller choices make it worse: the catalogue advertises the protected resource’s existence; the “lock” is implemented as a tool the same principal can call; and the server’s Origin check rejects the site’s own front-end while accepting any non-browser client (a plain HTTP client sends no Origin at all, and adding Mcp-Session-Id skips the check), so the control blocks only the legitimate UI.

Impact & severity

Severity: High.

Direct disclosure of everything registered on the server, from an unauthenticated-in-practice position. Here it is a flag; in a production deployment the same pattern exposes internal documents, API keys and configuration, and the “unlock” tool turns the disclosure into a two-step bypass that no prompt-level control can see. Because the access decision is a mutable state flag, it is also trivially replayable and shareable between sessions.

Mapping

OWASP Top 10 for LLM Applications 2025

  • LLM02:2025 — Sensitive Information Disclosure — protected data is readable by any client that can reach the server.
  • LLM06:2025 — Excessive Agency — a state-changing tool (“unlock”) stands in for an authorization check.

MITRE ATLAS

  • AML.T0057 LLM Data Leakage — the resource catalogue discloses protected content.
  • AML.T0055 Unsecured Credentials — the access decision is a guessable state flag.

Prevention

  • Keep protected data out of MCP catalogues: anything registered can be read; assume the catalogue is public.
  • Authorize on the resource, not the transport: re-check the caller’s policy at every read, in the backend that owns the data.
  • Never let the caller operate the lock: an access decision must not be a tool the same principal may invoke.
  • Treat MCP as a transparency interface: expose tooling and genuinely public resources only; keep secrets behind an authenticated API.
  • Do not use Origin/session checks as access control: they are CORS hygiene, not authorization, and are absent from every non-browser client.

Platform note shown after the solve (“lessons learned”)

MCP Server Resource Security

What happened: The MCP server exposed protected resources that users could access directly, bypassing intended access controls.

Why it's dangerous: MCP servers are designed to expose resources and tools to users. If you include protected or sensitive resources in an MCP server, users can read them directly, regardless of any authentication mechanisms you implement.

Prevention:

  • Never include protected resources in an MCP server - users can read them
  • Only expose public, non-sensitive resources through MCP servers
  • Keep sensitive data and protected resources on backend servers with proper access controls
  • Use MCP servers for tooling and public resources only
  • Implement proper separation between MCP resources and protected backend resources
  • Assume that anything exposed through an MCP server is accessible to users

Key lesson: Never include protected resources in an MCP server - users can read them. MCP servers are designed for transparency and user access, so any resources exposed through them should be considered public.

2.3 Blind Network Ninja — Blind OS Command Injection and Out-of-Band Exfiltration

Challenge: Advanced track, level 9 — Blind Network Ninja  ·  Vulnerability class: Blind OS command injection / out-of-band exfiltration  ·  Severity: Critical  ·  Verified flag: flag-788808

Mechanism

A single tool answers connectivity questions about a hostname. The string is concatenated into a shell probe and only Online/Offline is returned to the conversation, so the level is deliberately blind:

check_connectivity(hostname)
  -> subprocess: "ping -c 1 " + hostname     # user-controlled text reaches a shell

# safer pattern: call the library directly, never build a shell string
import ipaddress, socket
def check_connectivity(host):
    ipaddress.ip_address(host)              # strict character allowlist
    return socket.create_connection((host, PORT), timeout=2)

The exfiltration channel is the container’s own HTTP log viewer at /level/9/logs — a request made from inside the container is visible there even though nothing is returned in the chat.

Verified result

Exploited live and accepted by the platform. flag-788808  ·  a fresh container replayed the identical chain and issued flag-48f636  ·  the platform’s own status endpoint confirms the level is completed:

Root cause

User input is concatenated into a command string instead of being passed to a library call, so the shell — not the tool — decides what the input means. The tool’s stated purpose (a yes/no connectivity answer) gives no hint of the capability actually attached to it, which is the definition of excessive agency at the tool layer.

The second, subtler mistake is the belief that hiding the output makes the capability safe. Suppressing stdout removes the convenience of the exploit, not the exploit; the attacker simply chooses a channel the tool does not control. That belief is what makes this the “blind” variant of the same class.

Impact & severity

Severity: Critical.

Remote command execution as the container’s service user, with full read access to the level’s file system and its flag, plus whatever network reach the container has. In a real deployment, outbound access is nearly always available for *some* protocol, so exfiltration succeeds even under aggressive output filtering — and the same string can just as easily open a reverse shell.

Mapping

OWASP Top 10 for LLM Applications 2025

  • LLM05:2025 — Improper Output Handling — an unvalidated tool argument reaches a shell.
  • LLM06:2025 — Excessive Agency — a connectivity check can run arbitrary commands.

MITRE ATLAS

  • AML.T0053 LLM Plugin Compromise — the tool invocation path executes unauthorized commands.
  • AML.T0057 LLM Data Leakage — the out-of-band channel carries the data out.

Prevention

  • No shell concatenation: never build a shell command from user input; call the underlying library directly.
  • Validate strictly: restrict hostnames to a character allowlist and reject everything else.
  • Don’t trust silence: a tool that returns no output can still be dangerous — egress filtering and command auditing matter even when the chat shows nothing.
  • Scope the capability: a connectivity check should not be able to run a shell at all.
  • Constrain egress: restrict outbound connections from application containers so exfiltration has nowhere to go.

Out-of-Band Data Exfiltration

What happened: Even when command output is suppressed, data was exfiltrated through out-of-band channels (DNS queries, HTTP requests) to an attacker-controlled server.

Why it's dangerous: Attackers can extract sensitive data even when direct output is blocked, using side channels like network requests, DNS lookups, or timing attacks.

Prevention:

  • Prevent command injection at the source (same as Level 6)
  • Implement network egress filtering and monitoring
  • Restrict outbound network connections from application servers
  • Monitor DNS queries and HTTP requests for suspicious patterns
  • Use application-level firewalls to detect data exfiltration attempts

Key lesson: Suppressing output doesn't prevent data leakage. Attackers can use out-of-band channels to extract information. Prevention requires blocking the injection itself.

2.4 The Shape Shifter — Insecure Deserialization (unsafe YAML loader)

Challenge: Expert track, level 6 — The Shape Shifter  ·  Vulnerability class: Insecure deserialization (unsafe parser)  ·  Severity: Critical  ·  Verified flag: flag-8b34bd

Mechanism

The level offers a configuration processor: submit YAML, get a summary of the keys. The backend parses that document with a full loader — the equivalent of PyYAML’s yaml.load() rather than safe_load() — so the tag !!python/… is resolved into live Python objects and function calls instead of being rejected as data:

# vulnerable pattern
data = yaml.load(document)          # full loader: !!python/... tags build objects & call functions

# safer pattern
data = yaml.safe_load(document)     # plain data structures only; no object construction

Deserializing is not parsing: a safe parse yields data, while a permissive deserializer executes code as a by-product of rebuilding rich objects. The tool chose expressiveness over the much smaller trust boundary its actual use case needed.

Insecure Deserialization

What happened: The system used unsafe YAML deserialization (yaml.load() instead of yaml.safe_load()), allowing you to execute arbitrary Python code through !!python/object tags in the YAML payload.

  • Use Safe Deserializers: always use yaml.safe_load() instead of yaml.load() for untrusted data

2.5 The Octopus — Credential Leak and Cache/Parser-Differential Escalation

Challenge: Expert track, level 7 — The Octopus  ·  Vulnerability class: Credential leak in a tool error + writable authorization cache  ·  Severity: High  ·  Verified flag: flag-ce352f

Mechanism

Two components parse the same input differently, and a verbose error leaks a privileged value. A privileged tool (read_root_flag(session_id)) refuses a caller, but names the exact administrator key it wants. Separately, a user-facing cache-update tool accepts a JSON string and, a safety filter inspects one field (status) with a regex while a second parser reads another field (cache_task_id) to decide the session identity. Combining the two: upload the leaked key as a file, point the cache at it, and the privileged read now succeeds.

read_root_flag(session_id)      # requires a session key taken from cache
upload_file(content)            # attacker-controlled content → file_id
process_cache_update(json_string, session_id)   # filter reads "status"; cache reads "cache_task_id"

Root cause

Two separate hygiene failures compound each other.

  • Error paths are not held to the same disclosure standard as normal responses. The refusal message names the exact credential required — the attacker does not guess, the system hands over the key.
  • A cache is trusted as though it were an authorization decision. The session identity is read from a store the same untrusted caller can write, and it is never re-validated against the real policy at the moment of the privileged read. Caches are a performance optimization, not a security boundary.

Underneath sits a parser differential: the safety filter and the consuming parser disagree about which field matters, so the value that is validated is not the value that is applied. Validation that inspects a different grammar than the consumer is not validation.

Impact & severity

Severity: High.

Privilege escalation from an unauthenticated or low-privilege position, driven entirely by information the system itself leaked. Because session_id is attacker-supplied and never bound to the authenticated caller, any session can be targeted, and any tool result that leaks a required literal can be replayed the same way. In production this is a direct route to reading other tenants’ data or invoking privileged administrative tools.

Mapping

OWASP Top 10 for LLM Applications 2025

  • LLM02:2025 — Sensitive Information Disclosure — the tool’s error message hands over the credential.
  • LLM06:2025 — Excessive Agency — a cache entry is treated as equivalent to an authorization check.

MITRE ATLAS

  • AML.T0057 LLM Data Leakage — the required key is disclosed to the client.
  • AML.T0055 Unsecured Credentials — the leaked literal becomes the access grant.

Prevention

  • Scrub error output: messages returned to any client must never include tokens, keys, internal identifiers or stack traces; log them server-side only.
  • Re-authorize, don’t cache-trust: every privileged read must check the real authorization policy at read time, never a cached inference of a prior check.
  • Unify parsers: ensure every component that parses a given input agrees on the same grammar, to eliminate the differential.
  • Reject ambiguity: configure parsers to reject duplicate keys rather than silently choosing one.
  • Bind identity server-side: never let a caller nominate the session or identity that an authorization decision uses.

Parser Differential (JSON vs Regex)

What happened: A discrepancy between how the security filter (Regex) and the application parser (JSON) handled duplicate keys allowed malicious data to bypass checks.

Why it's dangerous: "Parser differentials" occur when two different systems interpret the same data differently. Here, the Regex saw the first "safe" status, but the JSON parser respected the last "error" status.

Prevention:

  • Canonicalization: Parse data into a standard object representation before validating it.
  • Avoid Duplicate Validations: Don't re-parse data after validation; pass the validated object forward.
  • Reject Ambiguity: Configure parsers to reject ambiguous input (e.g., duplicate JSON keys) rather than guessing.

Key lesson: Security checks must look at the data exactly as the consuming application will see it.

2.6 The Heist — TOCTOU Race Condition on a Consequential Action

Challenge: Expert track, level 8 — The Heist  ·  Vulnerability class: TOCTOU race condition / model-only guardrail  ·  Severity: High  ·  Verified flag: flag-14ab1b

Mechanism

A trading desk with $1000 offers two fragments at $1000 each. The tools read the balance, compare it, and deduct as separate, non-atomic operations:

get_balance()      -> reads the balance
create_order(x)    -> stages an order
execute_order(x)   -> checks balance >= cost, then deducts   # check and act are separate steps

Nothing outside the model’s own step-by-step reasoning prevents two executions from racing through that gap. Both tool calls are issued in a single turn, so both checks observe the pre-deduction balance and both actions commit.

Root cause

The only guardrail preventing a double-spend lives in the language model’s reasoning (“I should check the balance before approving a second order”) rather than in a deterministic, atomic operation enforced by the system — a database transaction, a lock, or an idempotency key.

Reasoning in natural language is not a concurrency control primitive: it can be reframed, distracted or simply raced, because it carries no atomicity guarantee at all. The instant the attacker moves “who decides” out of the model and into the backend (which performs no check), nothing in the system enforces the invariant.

Impact & severity

Severity: High.

Double-spend or double-execution of any action gated this way: financial loss, duplicate fulfilment, duplicated refunds or payouts, or any other consequence of a check being bypassed by concurrency rather than by subverting the model directly. Because the primitive is “issue two state-changing calls before the first commits”, it applies to every stateful tool the agent can call twice in a turn.

Prevention

  • Make the check-and-act atomic: balance checks and debits must happen inside a single transaction or be protected by a lock/idempotency key.
  • No reasoning-only guardrails: never rely on a model’s natural-language reasoning as the sole enforcement of a safety-critical invariant.
  • Idempotency by design: design tools so calling them twice with the same intent produces the same result once.
  • Re-check at execution: re-validate the precondition inside the tool immediately before the state change.
  • Assume concurrent tool calls: an agent can issue many calls in one turn; the backend must be correct under concurrency.

Time-of-Check to Time-of-Use (TOCTOU) / Race Condition

What happened: You forced the agent to process two transactions in parallel. Both checks saw sufficient funds ($1000) before either deduction occurred, allowing you to spend the same money twice.

Why it's dangerous: Agentic workflows often separate "Reasoning" (Check) from "Action" (Execution) by seconds or minutes. If the underlying state changes during this gap (e.g., balance updates), the agent acts on stale data.

Prevention:

  • Atomic Transactions: Use database transactions (ACID) to lock rows during updates.
  • Verify at Execution: Re-check the condition (Balance >= Cost) inside the execution tool, immediately before the update.
  • Sequential Processing: Force the agent to wait for confirmation of Action A before starting Reasoning for Action B.

3. Cross-Cutting Themes

Despite covering different technical bug classes, all six cases share a small number of underlying design mistakes.

  • Code/data confusion. User- or environment-controlled strings are passed to an interpreter, shell or deserializer that can execute arbitrary logic, instead of being validated against a narrow schema (Bad Robot, Blind Network Ninja, The Shape Shifter).
  • Authorization delegated to the wrong layer. A tool, resource or cache is treated as if it enforces a security decision, when none of them actually check policy at the moment it matters (Master of Resources, The Octopus, The Heist).
  • Excessive agency. Tools are given broader capability than their stated purpose requires — a calculator that can reach the file system, a connectivity check that can reach a shell, an order tool with no atomicity (all six, to varying degrees).
  • Verbose internals leak through side channels. Error messages, cache entries, interpreter exceptions and MCP resource listings are all disclosure surfaces that were never audited as such (Master of Resources, The Octopus — and, decisively, Bad Robot).
  • Suppression and refusal are mistaken for controls. Hiding tool output (Blind Network Ninja) and declining politely in natural language (The Shape Shifter, The Heist) stopped nothing; the capability underneath was unchanged.

4. Consolidated Recommendations

  • Treat all external input as data, never as code. Never pass user input to eval()/exec() or into a shell command string; use safe, schema-validated parsers and library calls instead of string concatenation.
  • Separate authentication from authorization. Authentication protects a page; it does not make every resource or tool behind that page safe to expose. Enforce authorization at the resource layer itself.
  • Scope tool capability to its stated purpose. Every tool should do the smallest thing a legitimate call could need, with no incidental capability (file access, shell access, arbitrary object construction) left switched on.
  • Make safety-critical invariants atomic, not advisory. Checks and the actions they gate must be one atomic operation enforced by the system, never two steps separated by model reasoning.
  • Audit every output surface for leakage. Scrub error responses — including interpreter errors and privilege denials — and treat caches as performance aids, not authorization decisions.
  • Blocklist filters do not work; allowlists and sandboxes do. The calculator’s substring filter was bypassed with a string concatenation; the only durable fix is to remove the capability.
  • Sandbox and least-privilege by default. Run tools with minimal file-system, network and credential scope so a single bug does not translate into full host or account compromise.

7. Conclusion

All six classes trace back to the same handful of root causes: input treated as code, authorization delegated to a component that cannot enforce it, tools scoped far wider than their purpose, and safety-critical checks left as advisory rather than atomic. None of these are exotic — they are well-understood classes (command injection, insecure deserialization, broken access control, TOCTOU races) that become newly dangerous when an autonomous agent is the one calling the vulnerable code path, often faster and with less friction than a human operator would apply. The three most instructive results here share one shape: the control was placed in the conversation, in a message, or in a filter, while the capability behind it was left untouched.
